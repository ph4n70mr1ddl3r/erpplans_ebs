## W519. POS Suspicious Transaction & AML Compliance Reporting

| Field | Detail |
|---|---|
| **Trigger** | Cash transaction ≥ PHP 500,000 (single or cumulative within 24 hours for same customer) OR system detects suspicious structuring pattern OR cashier/manager identifies suspicious customer behavior |
| **Frequency** | Rare — estimated 5–10 flagged transactions per year chain-wide for hardware retail; more likely at stores near construction hubs serving contractors |
| **Volume** | ~5–10 suspicious transaction reports (STRs) filed annually with AMLC |
| **Owner** | Compliance Officer (filing); Store Manager (initial documentation) |
| **Participants** | Cashier, Store Manager, Compliance Officer, AMLC (external) |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | **Threshold monitoring**: system automatically monitors all cash transactions at POS; if single cash transaction ≥ PHP 500,000: system flags transaction and alerts Store Manager via terminal notification; if same customer (identified via loyalty card, name, or vehicle plate) accumulates cash transactions ≥ PHP 500,000 within 24 hours across multiple transactions: system alerts Store Manager with structuring detection alert | System | — | Automated |
| 2 | **Transaction hold**: for flagged transactions, system allows transaction completion but places cash in temporary hold status; system prompts cashier to collect customer identification (government-issued photo ID) and record customer details (full name, ID type, ID number, address, contact number, nature of transaction/purpose of purchase) | Cashier | Store Manager | 5 min |
| 3 | Cashier completes customer identification form in system (or system auto-populates from loyalty member data if customer is enrolled); if customer refuses to provide identification: Store Manager is notified; transaction is completed but flagged as "Customer Refused ID" — Compliance Officer reviews within 24 hours | Cashier / Customer | Store Manager | 3 min |
| 4 | Store Manager reviews flagged transaction details: customer identity, transaction amount, items purchased, payment method, any prior flagged transactions for same customer; Store Manager assesses whether transaction appears legitimate (e.g., contractor bulk-buying materials for a project) or suspicious (e.g., purchasing high-value easily-resalable items with large cash, customer appears nervous or evasive) | Store Manager | — | 15 min |
| 5 | If Store Manager assesses transaction as **legitimate**: documents assessment with justification (e.g., "Contractor purchasing cement, rebar, and tiles for government project — presented purchase order from agency"); system records legitimacy determination with manager ID; no STR filed; transaction hold released; documentation retained for 5 years per AMLA record retention | Store Manager | — | 10 min |
| 6 | If Store Manager assesses transaction as **suspicious** or is unsure: Store Manager escalates to Compliance Officer within 24 hours; Compliance Officer reviews transaction details, customer history, and Store Manager's assessment | Store Manager / Compliance Officer | Compliance Officer | 30 min |
| 7 | Compliance Officer determines if Suspicious Transaction Report (STR) is warranted per AMLC guidelines; if yes: Compliance Officer prepares STR using AMLC online portal with required details (covered person information, customer information, transaction details, suspicious indicators, supporting documents) | Compliance Officer | CFO | 2 hours |
| 8 | Compliance Officer files STR with AMLC via online portal; system logs STR filing with AMLC reference number, filing date, and linked POS transaction(s) | Compliance Officer | CFO | 30 min |
| 9 | **Tipping-off prohibition**: system restricts visibility of STR filing — cashier and Store Manager who reported are NOT informed of STR filing status; only Compliance Officer and CFO have access to STR records; per AMLA Section 9, no person shall disclose to any customer that a STR has been or will be filed | System / Compliance Officer | CFO | Ongoing |
| 10 | Compliance Officer maintains STR register: all filed STRs with AMLC reference numbers, filing dates, transaction references, and status; register subject to AMLC examination during periodic compliance audits | Compliance Officer | CFO | Quarterly review |
| 11 | Annual: Compliance Officer conducts AML awareness training for all Store Managers and Assistant Store Managers (integrated with W51 training program); training covers AMLA requirements, red flags for suspicious transactions, customer identification procedures, tipping-off prohibition, and STR filing process | Compliance Officer | CFO | 2 hours/year |

### System Touchpoints
- Automatic cash transaction threshold monitoring: single transaction ≥ PHP 500,000 and cumulative 24-hour monitoring per customer (W519.1)
- Structuring detection: multiple transactions below threshold by same customer within 24 hours (W519.1)
- Customer identification form in POS with auto-populate from loyalty member data (W519.2–3)
- Transaction hold status for flagged transactions (W519.2)
- Legitimacy assessment documentation with manager ID and justification (W519.5)
- STR filing log with AMLC reference number and restricted visibility per tipping-off prohibition (W519.8–9)
- STR register for AMLC compliance audits (W519.10)
- Integration with W5B (in-store selling — transaction source), W17 (loyalty — customer identification), W37 (loss prevention — suspicious behavior escalation), W51 (training — AML awareness), W292 (employee master — training completion tracking), W354 (B2B AML screening — parallel process for trade accounts)

### Pain Points / Risks
- **False positives** — in hardware retail, PHP 500,000+ cash purchases by contractors are legitimate business transactions; excessive flagging wastes Store Manager and Compliance Officer time; system should learn to reduce false positives over time (e.g., whitelisting known trade account customers with verified business registration)
- **Customer friction** — requiring government ID for large cash purchases may irritate legitimate contractor customers who are time-sensitive; Store Manager must handle diplomatically
- **Tipping-off risk**: if Store Manager informs customer that their transaction was "flagged" or "reported," this constitutes a criminal offense under AMLA Section 9; training must emphasize prohibition; mitigated by CTL-265 (controlled execution — POS Compliance & Controls (PA-08.3))
- **Structuring detection limitations** — customers structuring across multiple terminals within same store or across multiple stores within 24 hours may evade detection if system does not aggregate across terminals and locations in real-time
- **Low volume but high stakes** — with only 5–10 reports/year, institutional knowledge is limited; process must be well-documented so any Store Manager can execute correctly


### Automation Opportunity
- System auto-monitor of "monitoring" (replaces manual Step 1).
- System auto-record of "record customer details" (replaces manual Step 2).
- System auto-review of "reviews within 24 hours" (replaces manual Step 3).

### Controls
- CTL-265 (ensure controlled execution — POS Compliance & Controls (PA-08.3).)

### Time Estimate
Legitimate transaction assessment: ~25 min (15 min review + 10 min documentation). Suspicious transaction escalation: ~1 hour for Store Manager (initial documentation + escalation call). STR preparation and filing: ~2.5 hours for Compliance Officer. Annual AML awareness training: 2 hours/session × ~200 Store Managers and Assistant Store Managers (delivered via e-learning + in-person regional sessions).

### Staffing Implication
- **No incremental store-level headcount** — suspicious transaction handling is a Store Manager responsibility (estimated 1–2 hours/year per store at most).
- **Compliance Officer** — existing Compliance Officer within Finance/Legal team handles STR filing; estimated 25–50 hours/year for AML POS-related activity (STR filing, register maintenance, training delivery).
- Annual AML awareness training absorbed by W51 training program (2 hours within annual training calendar).

## W520. Age-Restricted Product Verification & Compliance at POS

| Field | Detail |
|---|---|
| **Trigger** | Barcode scan of age-restricted SKU at POS or SCO |
| **Frequency** | Multiple daily per store — estimated 5–10 age-restricted transactions per store per day (solvents, thinners, spray paints, cutting tools, pesticides) |
| **Volume** | ~1,000–2,000 age-restricted transactions/day chain-wide |
| **Owner** | Cashier (verification); Store Manager (compliance oversight) |
| **Participants** | Cashier, Customer, Store Manager (escalation), Compliance Team (audit) |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | Customer brings age-restricted items to checkout; Cashier scans barcode; system identifies SKU as age-restricted from item master flag (per DENR/FPA-regulated chemicals, cutting tools, solvents list maintained in W252 item master) | Cashier / System | — | Per scan |
| 2 | System interrupts transaction flow: POS terminal displays full-screen age-verification prompt showing item name, minimum age requirement (18 for solvents, cutting tools, pesticides per FPA regulations; configurable per SKU), and "Request Government-Issued Photo ID" instruction to cashier | System | — | Automated |
| 3 | Customer-facing display shows "Age Verification Required" message (does not display specific product or reason to protect customer privacy) | System | — | Automated |
| 4 | Cashier verbally requests customer's government-issued photo ID (acceptable forms: Philippine driver's license, passport, PhilHealth ID, SSS ID, GSIS ID, COMELEC voter's ID, national ID, postal ID with photo) | Cashier | — | 30 sec |
| 5 | Cashier selects ID type from dropdown on POS terminal; enters customer date of birth from ID or scans ID barcode (if machine-readable) | Cashier | — | 30 sec |
| 6 | System calculates customer age from date of birth; if age ≥ minimum age requirement: system displays "VERIFIED — Age Confirmed" on cashier screen; customer display returns to transaction total; transaction proceeds | System | — | Automated |
| 7 | If age < minimum age requirement: system displays "DENIED — Customer Below Required Age" on cashier screen; customer-facing display shows "Transaction Restricted"; system removes age-restricted item(s) from transaction; remaining non-restricted items continue to checkout; Cashier informs customer that specific item(s) cannot be sold due to age restriction | Cashier / System | Store Manager | 30 sec |
| 8 | If customer cannot produce valid ID: system denies sale of age-restricted item(s) per same step 7 procedure; customer can still purchase non-restricted items in transaction | Cashier | — | 30 sec |
| 9 | System logs age verification event: transaction ID, SKU(s) verified, customer age or "No ID" status, cashier ID, verification result (verified/denied/no ID), timestamp; log available for DENR/FPA compliance audit | System | — | Automated |
| 10 | Monthly: Compliance Team runs age-restricted product compliance report — verification rate (% of age-restricted transactions where verification was completed), denial rate, "No ID" rate by store; stores with verification rate < 95% flagged for retraining (W518) | Compliance Team | Legal/Compliance Head | 1 hour/month |
| 11 | Quarterly: Store Manager conducts spot-audit: observes 5 random age-restricted transactions at checkout (or reviews CCTV W71 footage of age-restricted scans) to verify cashiers are following ID request and verification procedure; documents observations in compliance log | Store Manager | Regional Manager | 30 min/quarter |

### System Touchpoints
- Age-restricted SKU flag in item master (W252) with configurable minimum age per SKU or category (W520.1)
- Full-screen age verification prompt interrupting transaction flow at scan (W520.2)
- Customer-facing display "Age Verification Required" message (W520.3)
- ID type dropdown with acceptable Philippine government-issued ID types (W520.5)
- Age calculation from date of birth with automated verified/denied determination (W520.6–7)
- Age verification compliance log with transaction, SKU, customer age/no ID, cashier, result (W520.9)
- Monthly compliance report: verification rate, denial rate, "No ID" rate by store (W520.10)
- Integration with W5B (in-store selling — verification within checkout flow), W252 (item master — age-restricted flag), W37 (loss prevention — compliance log review), W518 (cashier training — age-restricted procedure training), W71 (CCTV — spot-audit footage), W501 (first aid — solvent abuse incident response)

### Pain Points / Risks
- **Cashier bypass risk**: cashiers may skip ID verification to avoid customer confrontation or speed up checkout, especially during peak hours; automated prompt mitigates but cashier can enter false DOB; quarterly spot-audits and verification rate monitoring deter bypass
- **Customer confrontation** — customers (especially older adults) may be offended when asked for ID; cashiers must be trained to explain calmly and consistently ("Ma'am/Sir, we are required by law to verify age for these products")
- **Scope of restricted items unclear** — not all Philippine retailers enforce age restrictions consistently; defining the exact SKU list that triggers verification requires legal review and regular updates as regulations change
- **SCO age verification** — self-checkout stations require SCO Attendant intervention for age verification (W516.6), adding to attendant workload; risk that attendant approves without proper ID check; mitigated by quarterly spot-audits and verification rate monitoring
- **ID fraud** — customers may present fake or borrowed IDs; cashiers are not trained forensic document examiners; system accepts DOB entry in good faith


### Automation Opportunity
- System auto-scan of "Customer brings age-restricted items to checkout" (replaces manual Step 1).
- System auto-request of "Request Government-Issued Photo ID" (replaces manual Step 2).
- System auto-post of "postal ID with photo" (replaces manual Step 4).

### Controls
- CTL-265 (ensure controlled execution — POS Compliance & Controls (PA-08.3).)
- operational: quarterly spot-audits and verification rate monitoring

### Time Estimate
~30–60 seconds per age-restricted transaction (30 sec ID request + 30 sec ID entry and system verification). Adds ~15–30 min/day to cashier workload per store at 5–10 age-restricted transactions/day. Monthly compliance report: 1 hour. Quarterly spot-audit: 30 min/store.

### Staffing Implication
- No incremental headcount — age verification adds ~30 sec per affected transaction, absorbed within cashier and Store Manager duties.
- Compliance Team time for monthly reporting: ~1 hour/month (absorbed by existing Compliance FTE).
- Quarterly spot-audit: ~30 min/quarter per Store Manager (200 stores × 30 min = 100 hours/quarter, absorbed within existing FTEs).

## W527. POS Tax Exemption Processing (Government / PEZA / Institutional)

| Field | Detail |
|---|---|
| **Trigger** | Customer presents tax exemption certificate at POS (government agency purchase order, PEZA-registered entity ID, diplomatic exemption letter, BIR tax exemption ruling) |
| **Frequency** | Occasional — varies significantly by store location; ~10–20 per store per month for stores near government centers, PEZA zones, or diplomatic areas; ~2–5 for other stores |
| **Volume** | ~640–1,450 tax-exempt transactions/month chain-wide (≈30 gov't-center stores × 10–20 + ~170 other stores × 2–5) |
| **Owner** | Cashier (processing); Store Manager (verification and approval) |
| **Participants** | Cashier, Store Manager, Customer, Finance Team (compliance review) |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | Customer presents tax exemption documentation at checkout: government agency purchase order with VAT exemption certification, PEZA-registered entity ID card, diplomatic exemption letter, or BIR tax exemption ruling with TIN | Customer | — | — |
| 2 | Cashier identifies customer in system: looks up customer account (if existing B2B account per W24) or creates temporary tax-exempt customer record (for one-time government purchases) | Cashier | — | 2 min |
| 3 | Store Manager verifies tax exemption documentation: confirms document validity (government letterhead, PEZA registration number, BIR ruling reference), checks expiry (if applicable), verifies customer identity matches document; approves tax exemption in system with manager ID | Store Manager | — | 5 min |
| 4 | System applies zero output VAT to the transaction: all eligible items recalculated with 0% VAT (net of VAT from SRP); customer display shows "TAX EXEMPT TRANSACTION" with exemption type; receipt prints tax exemption details (exemption type, certificate/reference number, verifying manager ID) | System | — | Automated |
| 5 | System posts transaction to tax-exempt revenue GL account (separate from standard VATable sales); records in tax-exempt transaction register for BIR reporting (W9A.16 VAT return — exempt/zero-rated sales schedule); zero output VAT entry posted alongside standard Dr. Cash / Cr. Revenue | System | — | Automated |
| 6 | If only some items are tax-exempt (partial exemption — e.g., PEZA-registered entity purchasing mixed merchandise where only certain categories qualify): Cashier manually flags exempt items at line level; system applies VAT only to non-exempt items | Cashier / System | Store Manager | 2 min |
| 7 | System logs tax exemption transaction: transaction ID, customer account, exemption type, certificate/reference number, verifying Store Manager ID, total exempt amount, items exempted; log available for Finance Team BIR audit support | System | — | Automated |
| 8 | Monthly: Finance Team reviews tax-exempt transaction register — total exempt sales by exemption type, by store, by customer; verifies documentation completeness for all exempt transactions; flags transactions missing documentation for Store Manager follow-up | Finance Team | Controller | 2 hours/month |

### System Touchpoints
- Tax-exempt customer identification: existing B2B account lookup or temporary tax-exempt customer record (W527.2)
- Tax exemption verification with Store Manager approval in system (W527.3)
- Zero output VAT application at line or transaction level with GL posting to exempt revenue account (W527.4–5)
- Partial exemption: line-level VAT flagging for mixed merchandise (W527.6)
- Tax-exempt transaction register with full documentation for BIR audit support (W527.7)
- Integration with W5B (in-store selling — tax exemption within checkout), W8 (AR processing — B2B account billing), W24 (credit application — customer VAT treatment classification), W253 (customer master — VAT registration status), W9A.16 (VAT return — exempt/zero-rated sales schedule), W54A (BIR CAS — compliant receipt format), W78 (government procurement — PHILGEPS integration)

### Pain Points / Risks
- **Document fraud** — forged tax exemption documents presented at POS; Store Manager is not a legal expert in document verification; system should maintain whitelist of verified tax-exempt entities from Finance Team
- **Partial exemption complexity** — PEZA and government exemptions may apply only to specific categories (e.g., capital equipment exempt, consumables taxable); Cashier must know which items qualify — requires product knowledge training
- **BIR audit exposure** — if tax-exempt transactions lack proper documentation or are incorrectly processed, BIR may disallow exemption during audit, resulting in VAT assessment + penalties + interest; Finance Team monthly review mitigates
- **Customer wait time** — tax exemption processing adds ~7 min to checkout (2 min customer lookup + 5 min manager verification); government agency buyers making large purchases accept this but institutional buyers making small purchases may be frustrated
- **Store Manager availability** — every tax-exempt transaction requires Store Manager verification; during peak hours, Store Manager may be unavailable, delaying checkout


### Automation Opportunity
- System auto-document of "documentation at checkout" (replaces manual Step 1).
- System auto-record of "Cashier identifies customer in system" (replaces manual Step 2).
- System auto-validate of "Store Manager verifies tax exemption documentation" (replaces manual Step 3).

### Controls
- CTL-265 (ensure controlled execution — POS Compliance & Controls (PA-08.3).)
- operational: should maintain whitelist of verified tax-exempt entities from Finance Team

### Time Estimate
~7 min per tax-exempt transaction (2 min customer lookup + 5 min verification and approval). Processing and posting: automated. Monthly Finance review: ~2 hours. At 10–20 transactions/store/month, total store-level labor is ~70–140 min/month per store.

### Staffing Implication
- No incremental headcount — tax exemption processing is a Cashier and Store Manager responsibility.
- Finance Team monthly review: ~2 hours/month absorbed by existing Finance FTE.
- Higher-volume stores (near government centers, PEZA zones) may see ~20 tax-exempt transactions/month adding ~140 min to Cashier/Manager workload.

## W529. POS Void & Refund Tiered Authorization

| Field | Detail |
|---|---|
| **Trigger** | Cashier initiates void (pre- or post-tender) or refund at POS |
| **Frequency** | Multiple daily per store — estimated 2–5 voids/refunds per store per day |
| **Volume** | ~400–1,000 voids/refunds/day chain-wide |
| **Owner** | Cashier / Store Manager |
| **Participants** | Cashier, Department Supervisor, Assistant Store Manager, Store Manager, Regional Manager (by tier) |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | Cashier identifies need for void or refund: customer request, pricing error, wrong item scanned, duplicate scan, post-purchase return; Cashier selects "Void" or "Refund" on POS terminal | Cashier | — | 15 sec |
| 2 | System determines authorization tier based on void/refund amount: **Tier 1 — Department Supervisor**: ≤ PHP 5,000 (covers most common voids — wrong item, duplicate scan, minor pricing error); **Tier 2 — Assistant Store Manager**: > PHP 5,000 and ≤ PHP 20,000; **Tier 3 — Store Manager**: > PHP 20,000 and ≤ PHP 100,000; **Tier 4 — Regional Manager**: > PHP 100,000 (rare — large trade account returns, high-value project material returns) | System | — | Automated |
| 3 | System prompts Cashier for void/refund reason code (Wrong Item Scanned / Duplicate Scan / Pricing Error / Customer Changed Mind / Customer Dissatisfied / Damaged Item / Other); Cashier selects reason code | Cashier | — | 15 sec |
| 4 | System displays required authorizer name and role on cashier screen (e.g., "Authorization Required: Dept. Supervisor — Maria Santos"); Cashier calls or signals the required authorizer to terminal | System / Cashier | — | 1 min |
| 5 | Authorizer arrives at terminal; swipes/scan employee ID badge or enters credentials; system verifies authorizer has required role (Department Supervisor / Asst. Manager / Store Manager / Regional Manager); system displays void/refund details (original transaction, amount, reason code, items) for authorizer review | Authorizer | — | 1 min |
| 6 | Authorizer reviews void/refund request: verifies amount is reasonable for stated reason, checks for patterns (same cashier repeatedly voiding, same customer returning frequently), confirms item(s) are present for refund (if applicable); Authorizer approves or rejects | Authorizer | — | 1–2 min |
| 7 | If approved: system processes void (reverses inventory, payment, loyalty points, promo usage per W5B.10) or refund (processes refund to original tender per W12A.6); system records authorization with: authorizer ID, authorizer role, approval timestamp, void/refund amount, reason code, original transaction reference | System | — | Automated |
| 8 | If rejected: system cancels void/refund request; Cashier informs customer of denial and alternative options (e.g., exchange instead of refund, escalate to Store Manager if Department Supervisor denied); system logs rejected request with reason | System / Cashier | — | 30 sec |
| 9 | **No available authorizer**: if required-tier authorizer is not physically available in store (e.g., Store Manager is the only Tier 3 authorizer and is off-site): Cashier can request remote authorization — system sends authorization request to authorizer's mobile device (push notification with transaction details); authorizer reviews and approves/rejects on mobile; all remote authorizations are logged with GPS location and timestamp of authorization device | System / Authorizer | — | 5 min |
| 10 | Daily: system generates void/refund summary report for Store Manager — count and total value by authorization tier, by reason code, by cashier, by authorizer; Store Manager reviews as part of W522 daily transaction review; Regional Manager receives daily summary of all Tier 4 authorizations (> PHP 100,000) | System | — | Automated |

### System Touchpoints
- Configurable tiered authorization matrix by void/refund amount with role-based access control (W529.2)
- Void/refund reason code selection with configurable reason code list (W529.3)
- Authorizer identification via employee ID badge/credentials with role verification (W529.5)
- Full authorization audit trail: authorizer ID, role, timestamp, amount, reason, original transaction (W529.7)
- Remote authorization capability via mobile push notification with GPS tracking (W529.9)
- Daily void/refund summary by tier, reason, cashier, authorizer (W529.10)
- Integration with W5B.10 (void transaction — reversal logic), W12A (in-store returns — refund processing), W101 (customer refund & credit — credit memo), W272 (cashier over/short — variance feed), W37 (loss prevention — void/refund pattern analysis), W522 (daily transaction review — void/refund summary), W152 (IT provisioning — role-based access), W292 (employee master — authorization role assignment)

### Pain Points / Risks
- **Authorizer bottleneck** — at stores where only Store Manager holds Tier 3 authority, voids/refunds > PHP 20,000 wait for Store Manager availability; customer wait time increases; remote authorization mitigates but requires mobile infrastructure
- **Tier circumvention** — Cashier and Supervisor colluding to split a large void into multiple smaller voids below PHP 5,000 to avoid higher-tier authorization; system should flag multiple same-customer voids within a session
- **Remote authorization security** — mobile push authorization could be compromised if authorizer's device is lost or stolen; GPS tracking and biometric device lock mitigate
- **Customer perception** — customer waiting at terminal while authorizer is called feels like being suspected of fraud; Cashier should communicate naturally ("Let me get my supervisor to authorize this for you — standard procedure for this amount")
- **Weekend/after-hours coverage** — stores open on weekends or late evening may not have all tier authorizers on shift; weekend scheduling (W34) must ensure at least one Tier 3 authorizer is always present


### Automation Opportunity
- System auto-scan of "scanned, duplicate scan, post-purchase return" (replaces manual Step 1).
- System auto-count of "account returns, high-value project material returns" (replaces manual Step 2).
- System rule-based authorization of "authorizer name and role on cashier screen" (replaces manual Step 4).

### Controls
- CTL-265 (ensure controlled execution — POS Compliance & Controls (PA-08.3).)
- operational: should flag multiple same-customer voids within a session

### Time Estimate
~3–5 min per void/refund (15 sec initiation + automated tier check + 15 sec reason code + 1 min authorizer call + 1–2 min review + automated processing). Remote authorization adds ~5 min. Daily summary review: part of W522 (~5 min of the daily review covers voids/refunds). Chain-wide at 400–1,000/day: ~20–80 hours/day for void/refund processing.

### Staffing Implication
- No incremental headcount — void/refund authorization is absorbed by existing management structure (Supervisors, Asst. Manager, Store Manager).
- Remote authorization availability requires Store Manager or Asst. Manager to have mobile device with push notification capability during all hours store is open.
- Weekend scheduling must ensure at least one Tier 3 authorizer (Store Manager or Asst. Manager) is always on shift.

## W530. POS High-Value Transaction Documentation & Customer ID

| Field | Detail |
|---|---|
| **Trigger** | Transaction total exceeds configurable threshold (default: PHP 50,000) |
| **Frequency** | Several per store per day — hardware retail has inherently high basket values (contractors, project buyers); ~1–3 high-value transactions per store per day (the PHP 50K trigger is self-limiting vs the ~PHP 840K/day per-store revenue canon) |
| **Volume** | ~200–600 high-value transactions/day chain-wide |
| **Owner** | Cashier (processing); Store Manager (oversight) |
| **Participants** | Cashier, Customer, Store Manager, Loss Prevention (analytics) |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | Transaction total exceeds PHP 50,000 (configurable per store or chain-wide); system displays "High-Value Transaction — Customer Identification Required" prompt on cashier screen | System | — | Automated |
| 2 | Customer-facing display shows "Transaction requires ID verification — please have your government ID ready" | System | — | Automated |
| 3 | Cashier verbally requests customer's government-issued photo ID; acceptable ID types: Philippine driver's license, passport, national ID (PhilSys), SSS ID, GSIS ID, COMELEC voter's ID, postal ID with photo, PRC ID, PhilHealth ID | Cashier | — | 30 sec |
| 4 | Cashier selects ID type from dropdown on POS terminal; enters ID number (or scans ID barcode if machine-readable); enters customer full name from ID | Cashier | — | 1 min |
| 5 | System records customer identification details against transaction: ID type, ID number (encrypted in audit log, last 4 digits visible), customer name, cashier ID, transaction ID, transaction amount; identification details printed on merchant copy of receipt (not on customer copy for privacy) | System | — | Automated |
| 6 | Transaction proceeds to tender per standard W5B.7; if payment is cash and amount ≥ PHP 500,000: W519 AML reporting process is triggered in addition to high-value documentation | Cashier / System | — | Per W5B |
| 7 | For loyalty members: system auto-populates customer name from loyalty record; Cashier only needs to verify and scan/enter ID — reduces data entry to ~30 sec | System / Cashier | — | 30 sec |
| 8 | Daily: high-value transaction register included in W522 daily review; Store Manager spot-checks high-value transactions for reasonableness (customer name matches purchase type, e.g., contractor buying construction materials) | Store Manager | — | Part of W522 |
| 9 | Weekly: Loss Prevention reviews high-value transaction register for anomalies: same customer name with different IDs, same ID at multiple stores, high-value transactions followed by high-value returns (W12), high-value cash transactions (W519 trigger correlation) | LP Analyst | LP Director | 1 hour/week |

### System Touchpoints
- Configurable high-value transaction threshold (default PHP 50,000) with automatic prompt (W530.1)
- Customer-facing display notification for high-value ID requirement (W530.2)
- ID type dropdown with Philippine government-issued ID types (W530.4)
- Customer identification recording: ID type, encrypted ID number, customer name linked to transaction (W530.5)

## W1305. Catch-Weight & Variable-Quantity Item POS Pricing Verification & Scale Calibration Compliance

| Field | Detail |
|---|---|
| **Trigger** | Quarterly scale calibration schedule; or customer complaint about weight-based pricing; or BIR/DENR inspection advisory |
| **Frequency** | Quarterly calibration per store (200 stores × ~4 scales each = ~800 calibrations/quarter); daily price verification for catch-weight items |
| **Volume** | ~800 scales chain-wide (200 stores × 4: lumber yard scale, hardware bulk scale, produce/garden scale, receiving dock scale); ~5,000 catch-weight SKUs (~14% of active SKUs) |
| **Owner** | Store Manager |
| **Participants** | Department Supervisor, Maintenance/Utility Staff, Scale Calibration Technician (contracted), POS System Administrator |

### Background

BuildRight sells catch-weight items — products sold by variable weight or length rather than by fixed unit. These include: (a) lumber (sold per board foot or per piece with variable dimensions), (b) nails and screws in bulk (sold per kilogram from bins), (c) wire and cable (sold per meter from spools), (d) chain and rope (sold per meter), (e) garden soil and sand (sold per kilogram). At POS, these items are weighed on a scale or measured, and the price is calculated by weight × price/kg or length × price/meter. Under Philippine law (BIR Revenue Regulations on weighing and measuring devices, DTI-BPS / DOST-ITDI NML standards per RA 9236), commercial scales must be: (i) verified and sealed by the local government weights and measures office, (ii) calibrated regularly (quarterly minimum for retail), (iii) accurate within prescribed tolerances. An inaccurate scale means customers are either overcharged (violating the Consumer Act, RA 7394) or undercharged (BuildRight loses revenue). This workflow manages scale calibration compliance and catch-weight pricing verification to ensure accurate customer billing and regulatory compliance.

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | **Daily catch-weight price verification**: (a) during opening procedure (W5A), Department Supervisor verifies catch-weight prices at POS: (i) test-weigh a known-weight item (calibration weight) on each store scale — verify displayed weight matches within ± 10g tolerance, (ii) verify price-per-unit for top 20 catch-weight items matches current ERP price: lumber price per board foot, nails price per kg, wire price per meter, (iii) scan catch-weight barcode label from a pre-printed test label — verify POS displays correct item, weight, and price calculation; (b) log verification results in daily checklist; (c) if any discrepancy: (i) price error: report to Store Manager for immediate correction in POS — price update pushed from ERP, (ii) scale inaccuracy: take scale out of service and use backup scale pending calibration | Department Supervisor | Store Manager | 10–15 min/day |
| 2 | **Quarterly professional scale calibration**: (a) contracted Scale Calibration Technician visits each store quarterly per maintenance schedule (W47); (b) technician calibrates each scale using NIST-traceable calibration weights: (i) zero-point verification, (ii) linearity test (test at 25%, 50%, 75%, 100% of scale capacity), (iii) repeatability test (same weight weighed 5 times — must be within ± 0.1% of reading); (c) if scale fails calibration: (i) attempt adjustment per manufacturer procedure, (ii) if adjustment fails: scale replaced from spare inventory at regional office, failed scale sent for repair; (d) technician issues calibration certificate per scale with: scale serial number, calibration date, test results, next calibration due date, technician signature and accreditation number; (e) calibration certificate filed in Oracle eAM (fit-gap F5) and displayed near scale (LGU inspection requirement) | Scale Calibration Technician | Store Manager | 1–2 hours/store/quarter |
| 3 | **LGU weights & measures inspection readiness**: (a) when LGU announces weights and measures inspection: Store Manager ensures: (i) all scales have current calibration certificates displayed, (ii) LGU verification seals (lead wire seal on scale adjustment mechanism) are intact — broken seal indicates potential tampering, (iii) catch-weight price labels are clearly displayed per DTI requirements (price per kg, price per meter, price per board foot), (iv) scale display is visible to customer during weighing (Consumer Act requirement), (v) receipt shows item, weight, unit of measure, price per unit, and total price for catch-weight items; (b) LGU inspector may: (i) test scales with their own calibration weights, (ii) verify price accuracy for catch-weight items, (iii) issue compliance certificate or notice of violation; (c) for violations: Store Manager has 5 days to correct; uncorrected violations result in fines and potential store closure per LGU ordinance | Store Manager | VP Legal & Compliance | Per inspection: 2–3 hours |
| 4 | **Catch-weight inventory accuracy reconciliation**: Weekly, Department Supervisor reconciles catch-weight inventory: (a) for bulk items (nails, screws by kg): compare POS sales volume (total kg sold per SKU per week) to physical bin inventory change; (b) for lumber: compare POS board foot sales to physical count change; (c) investigate variances > 3%: (i) scale inaccuracy (over- or under-weighing), (ii) measurement rounding at POS, (iii) spillage/waste not recorded, (iv) pilferage; (d) post inventory adjustment per threshold with Store Manager approval | Department Supervisor | Store Manager | 1–2 hours/week |
| 5 | **Catch-weight pricing change management**: When Category Manager changes catch-weight item prices: (a) system pushes price update to all POS terminals in real-time (continuous sync per POS-013); (b) Department Supervisor receives notification of price change with effective date/time; (c) Supervisor updates shelf/bin price labels for catch-weight items before first customer transaction at new price; (d) system prevents sale of catch-weight item at old price after effective time — auto-rejects if POS cache has stale price; (e) price change log maintained for BIR audit trail (price history per SKU with dates) | System / Department Supervisor | Category Manager | Per price change event: 15–30 min |

### System Touchpoints
- POS scale integration — scale weight transmitted to POS for price calculation
- ERP price management — catch-weight item pricing with per-unit-of-measure rates
- Calibration certificate management — digital filing and renewal tracking per W47
- Inventory module — catch-weight inventory tracking with unit of measure (kg, meter, board foot)
- BIR-compliant receipt generation — catch-weight item detail on receipt
- Price push notification — real-time price update to POS terminals
- LGU inspection log — inspection dates, results, corrective actions

### Pain Points / Risks
- **Scale drift between calibrations** — scales gradually drift out of calibration due to wear, temperature changes, and vibration; daily verification catches significant drift but minor drift accumulates between quarterly professional calibrations
- **Customer trust** — customers who suspect they are being overcharged for catch-weight items (especially contractors buying bulk nails or lumber) may dispute the weight; visible scale display and customer-facing weight readout reduce disputes
- **Humidity and corrosion** — Philippine humidity accelerates scale corrosion, especially in the outdoor lumber yard; load cells in outdoor scales have shorter lifespans and require more frequent replacement
- **BIR audit risk**: if BIR finds catch-weight pricing errors during a CAS audit (W1304), BuildRight may be assessed for underreported VAT (if weight was understated) or penalized for consumer fraud (if overstated); mitigated by the Store Manager review and approval gate and operational: periodic reconciliation against source documents

- **Maintenance/Utility Staff**: ~30 min/quarter during calibration visits

## W1516. Philippine BIR Electronic Invoicing System (EIS) Sales Data Transmission & Compliance

| Field | Detail |
|---|---|
| **Trigger** | Each POS sales transaction completion; BIR EIS daily/weekly batch submission deadlines |
| **Frequency** | Continuous real-time or near-real-time per transaction; daily batch reconciliation to BIR EIS portal |
| **Volume** | ~2.8M POS transactions/month across 200 stores (~467/store/day) |
| **Owner** | Tax Compliance Manager |
| **Participants** | Tax Compliance Manager, IT POS Team, Finance Controller, Store Department Supervisor |

### Background

The Philippine Bureau of Internal Revenue (BIR) is progressively mandating Electronic Invoicing/Receipting under the TRAIN Law (RA 10963) for taxpayers exceeding PHP 3M annual gross sales. BuildRight Depot, with ~PHP 62.3B annual revenue, falls well within the mandatory scope. The BIR Electronic Invoicing System (EIS) requires registered businesses to transmit sales data (transaction-level details including TIN, amount, VAT, item descriptions) electronically. Non-compliance carries penalties of PHP 1,000–50,000 per violation plus potential suspension of business permit. For a retailer processing 2.8M monthly transactions across 200 stores, the technical and compliance challenge is significant: every POS must generate BIR-compliant electronic sales data, transmit to a centralized system, and reconcile against BIR portal acknowledgment — all while maintaining offline capability during Philippine internet outages.

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | **BIR EIS registration and setup**: (a) Tax Compliance Manager registers each store location (200 stores + 4 DCs + HQ) with BIR EIS portal; (b) receives unique facility TIN-EIS credentials; (c) IT POS Team configures each POS terminal to generate BIR-compliant sales data fields: (i) seller TIN, (ii) registered name, (iii) store address, (iv) transaction date/time, (v) item description per line, (vi) quantity, (vii) unit price, (viii) VAT amount, (ix) total amount, (x) official receipt/invoice number per BIR sequential format | Tax Compliance Manager / IT POS Team | Finance Controller | Initial setup: 2–3 months |
| 2 | **Per-transaction data generation**: (a) POS system generates electronic sales record for each completed transaction with all BIR-mandated fields; (b) system assigns BIR-compliant sequential OR/SI number; (c) record stored in local queue (for offline resilience) and queued for transmission to BIR EIS; (d) customer receipt printed with BIR-required details including "TIN: xxx-xxx-xxx" header, "VAT Registered" marker, and QR code linking to electronic record | System | — | Automated per transaction |
| 3 | **Data transmission**: (a) system transmits queued sales records to BIR EIS via API/SFTP in real-time (preferred) or batch mode (minimum daily); (b) for stores experiencing internet outage: records queued locally and transmitted upon connectivity restoration within 24-hour tolerance window; (c) system logs transmission status: sent, acknowledged, rejected (with rejection reason) | System / IT POS Team | Tax Compliance Manager | Automated |
| 4 | **Daily reconciliation**: (a) Tax Compliance Manager or designee runs daily EIS reconciliation report: (i) total transactions in POS system vs. total records transmitted to BIR EIS, (ii) records acknowledged by BIR vs. pending/rejected, (iii) sequential OR number gap analysis (no missing OR numbers per BIR requirement); (b) for rejected records: IT POS Team investigates rejection reason (format error, missing field, duplicate OR number), corrects, and retransmits; (c) for transmission gaps (offline stores): verify all records queued during outage were transmitted upon reconnection | Tax Compliance Manager / IT POS Team | Finance Controller | 30–60 min/day |
| 5 | **Monthly compliance certification**: (a) Tax Compliance Manager generates monthly EIS compliance report: (i) total transactions submitted vs. total POS transactions (target: 100%), (ii) rejection rate (target: < 0.1%), (iii) average transmission latency (target: < 4 hours), (iv) sequential OR number integrity confirmation; (b) Finance Controller reviews and signs off; (c) report filed for BIR audit readiness (10-year retention per A6.5) | Tax Compliance Manager | Finance Controller | 2–3 hours/month |
| 6 | **BIR audit response**: when BIR selects BuildRight for EIS compliance audit: (a) Tax Compliance Manager extracts requested transaction samples from system; (b) provides transmission logs, acknowledgment receipts, and sequential OR number continuity evidence; (c) coordinates with external tax counsel if BIR raises deficiencies | Tax Compliance Manager | CFO | Per audit event |

### System Touchpoints
- POS transaction engine: BIR-compliant electronic sales record generation with all mandated fields (W1516.2)
- BIR EIS API/SFTP integration: real-time or batch transmission with acknowledgment tracking (W1516.3)
- Local queue management: offline transaction queuing with automatic flush upon connectivity restoration (W1516.3)
- Daily reconciliation module: POS transaction count vs. BIR EIS submission count, sequential OR gap analysis (W1516.4)
- Monthly compliance dashboard: submission rate, rejection rate, latency metrics (W1516.5)
- Integration with W540 (BIR Invoice Reprint), W530 (High-Value Transaction Documentation), POS-042 (event-driven architecture)

### Pain Points / Risks
- **Offline store transmission gaps**: with Philippine internet reliability challenges (POS offline ≥ 8 hours per A6.1), stores in prolonged outage risk exceeding the 24-hour EIS transmission tolerance; BIR may impose penalties even if the delay is ISP-caused
- **Sequential OR number integrity**: BIR strictly prohibits gaps in OR/SI numbering; if a POS terminal crashes mid-transaction and generates a partial record, the OR number may be consumed without a corresponding BIR submission — requires manual void explanation and documentation
- **Volume at scale**: 2.8M transactions/month × 10+ data fields = massive data payload to BIR EIS; API rate limits, transmission failures, and rejection handling at this volume require robust automated error recovery
- **Regulatory uncertainty**: BIR EIS implementation timeline has been repeatedly extended; requirements may change, requiring costly POS software updates across 600 terminals (200 stores × 3 terminals)
