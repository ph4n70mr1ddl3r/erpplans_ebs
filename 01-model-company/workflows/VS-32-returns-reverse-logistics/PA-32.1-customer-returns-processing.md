## W1622. In-Store Customer Return Processing

| Field | Detail |
|---|---|
| **Trigger** | Customer brings purchased item(s) to customer service counter for return |
| **Frequency** | ~56,000 returns/month across 200 stores (~2% return rate on 2.8M transactions) |
| **Volume** | ~280 returns/store/month (~9/day); seasonal spikes post-promotion |
| **Owner** | Customer Service Representative (CSR) |
| **Participants** | CSR, Customer Service Manager, Store Manager (overrides) |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | Customer presents item(s) and receipt (or loyalty card/transaction reference) at customer service counter; CSR scans receipt barcode or looks up transaction by date/loyalty card/amount | CSR | — | 2 min |
| 2 | System retrieves original transaction: (a) verifies item was purchased at this store (or BuildRight network — cross-store returns accepted), (b) checks return eligibility: (i) within 30-day return window (standard items), (ii) 7-day return window for appliances and power tools, (iii) non-returnable items: paint (custom mixed), cut-to-length items (wire, lumber, pipe), clearance/final sale items, (c) checks item has not been previously returned for same transaction | System | — | Automated |
| 3 | CSR inspects returned item: (a) matches item to receipt line (SKU, description), (b) checks condition: unused, original packaging, all accessories included, (c) checks for damage (if damaged: route to W1626 for quality assessment), (d) for electrical items: verifies safety seals intact, (e) for power tools: checks for signs of use (bit wear, scratches on chuck) | CSR | Customer Service Manager | 3 min |
| 4 | **Accept**: CSR processes return in system: (a) scans item barcode, (b) selects return reason code (14 codes: unwanted, wrong size, found cheaper, defective, damaged in transit, wrong item, missing parts, not as described, quality issue, duplicate purchase, gift return, installation incompatibility, buyer's remorse, other), (c) system creates return receipt with authorization number | CSR | — | 2 min |
| 5 | Refund method selection (per BuildRight policy): (a) original tender refund — cash for cash purchase, card refund for card purchase, (b) store credit (gift card) for returns > 30 days or without receipt (per W1625), (c) exchange for different item (per W1624) | CSR | Customer Service Manager | 1 min |
| 6 | System processes: (a) inventory added back to store available stock (if resaleable condition — "Return to Stock" status), or moved to "Damaged/Defective" status (per W91), or moved to "Quarantine" for quality review (per W1626), (b) refund/payment reversal processed, (c) return transaction posted to GL (contra-revenue, inventory adjustment), (d) loyalty points reversed if points were earned on original purchase | System | — | Automated |
| 7 | Customer signs return receipt (digital signature pad or paper); CSR returns item to designated returns staging area; resaleable items returned to shelf within 2 hours by Stock Associate | CSR / Stock Associate | Customer Service Manager | 2 min + restock time |

### System Touchpoints
- Transaction lookup by receipt barcode, loyalty card, date/amount, or transaction number (W1622.1)
- Return eligibility engine with configurable rules per category (W1622.2)
- Return reason code taxonomy (W1622.4)
- Inventory status routing: Return to Stock / Damaged / Quarantine (W1622.6)
- Loyalty points reversal (W1622.6)
- GL posting for return transaction (contra-revenue, inventory adjustment) (W1622.6)
- **Custody & precedence** (per the [Event Custody & Precedence Register](../event-custody-and-precedence-register.md), E-09): this value stream owns return *decisioning* (eligibility, approval tiers, credit issuance, disposition); POS-side execution rides VS-08 (multi-tender refund mechanics W1538; fraud screening W605), and the cross-store variant runs VS-07 W12 with its higher Store-Manager approval threshold (above PHP 5,000)

### Pain Points / Risks
- **Return fraud**: Customers returning stolen merchandise, used items as new, or items purchased on promotion at full price after promo ends; W1628 addresses detection
- **Cross-store return complexity**: Items purchased at one store and returned at another create inter-store inventory imbalance; periodic inter-store reconciliation needed
- **Restock delay**: Returned items sitting in staging area rather than being returned to shelf quickly reduce available inventory for sale
- **Custom items**: Paint (custom mixed), cut lumber, cut wire are non-returnable but customers may dispute; clear signage and receipt notation required


### Automation Opportunity
- System auto-scan of "scans receipt barcode or looks up transaction by date/loyalty card/amount" (replaces manual Step 1).
- System auto-validate of "checks return eligibility" (replaces manual Step 2).
- System auto-inspect of "inspects returned item" (replaces manual Step 3).

### Controls
- CTL-179 (ensure returns integrity & refund-fraud prevention.)
- operational: Customer Service Representative review and approval gate

### Time Estimate
~10 min per return (including inspection, system processing, and customer interaction); ~280 returns/store/month × 10 min = ~47 hours/store/month

### Staffing Implication
At ~47 hours/month of return processing per store, 1 dedicated CSR can handle returns plus other customer service duties (BOPIS pickup, special orders, complaints). Current staffing model (1 CSR per store) is adequate.

## W1624. Customer Exchange Processing

| Field | Detail |
|---|---|
| **Trigger** | Customer requests exchange (different size, color, or item) instead of refund |
| **Frequency** | ~15,000 exchanges/month (~27% of returns result in exchange) |
| **Volume** | ~75 exchanges/store/month |
| **Owner** | CSR |
| **Participants** | CSR, Customer Service Manager |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|--- |---|
| 1 | Customer requests exchange during return process (W1622 step 4); selects replacement item — same SKU different variant (size, color) or different SKU within same category | CSR | — | 2 min |
| 2 | System checks: (a) requested exchange item availability at current store, (b) if not available at current store: checks nearby stores (within 30 km) or offers home delivery from DC, (c) price difference calculation: (i) same price item — even exchange, (ii) higher price item — customer pays difference, (iii) lower price item — customer receives store credit for difference (no cash refund on exchange) | System | — | Automated |
| 3 | CSR processes exchange: (a) scans returned item (return transaction), (b) scans new item (sale transaction), (c) system creates linked exchange transaction (return + sale), (d) price difference collected or store credit issued | CSR | — | 3 min |
| 4 | Inventory: returned item added back to stock; exchanged item deducted from stock; net inventory impact is zero if same SKU variant, or one SKU increase / one SKU decrease | System | — | Automated |

### System Touchpoints
- Exchange availability check with nearby store lookup (W1624.2)
- Linked exchange transaction (return + sale) with price difference handling (W1624.3)


### Pain Points / Risks
- **Inventory-asymmetry risk**: cross-SKU exchanges (different item, same category) shift stock mix while looking value-neutral; mitigated by the linked return + sale exchange transaction recording the net one-SKU-up/one-SKU-down impact (step 3)
- **Dead-end risk**: the replacement is unavailable at the current store and the exchange converts to a lost sale; mitigated by the nearby-store (30 km) availability check and home-delivery option for the replacement (step 2)

### Automation Opportunity
- System auto-request of "requests exchange during return process" (replaces manual Step 1).
- System auto-validate of "checks" (replaces manual Step 2).
- System auto-scan of "scans returned item" (replaces manual Step 3).

### Controls
- CTL-337 (ensure controlled execution — Customer Returns Processing (PA-32.1).)
- operational: standard operating procedures; system-enforced validation rules

### Time Estimate
~5 min per exchange (request handling 2 min + exchange processing 3 min; availability check and inventory postings automated) × ~15,000 exchanges/month ≈ 15,000 hours/year of CSR time (~75 exchanges/store/month).

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|

| 2 | If transaction found: process as standard return per W1622 | CSR | — | Per W1622 |
| 3 | If transaction not found: CSR processes no-receipt return: (a) verify item is a BuildRight-carried SKU (system lookup), (b) check item condition (unused, original packaging), (c) system applies no-receipt return policy: (i) refund limited to current selling price or lowest price in last 90 days (whichever is lower) to prevent fraud, (ii) refund issued as store credit only (no cash/card refund), (iii) customer must present valid government ID (recorded in system for fraud tracking), (iv) limit: max 3 no-receipt returns per customer per 6-month period | CSR | Customer Service Manager | 5 min |
| 4 | System records no-receipt return against customer ID (government ID number); updates no-receipt return counter; blocks further no-receipt returns if limit exceeded | System | — | Automated |
| 5 | Store credit (gift card) issued for refund amount; customer can use immediately | CSR | — | 2 min |

### System Touchpoints
- Transaction search by multiple criteria (W1625.1)
- No-receipt return policy engine with lowest-price calculation (W1625.3)
- Customer ID tracking with return frequency counter (W1625.4)
- Store credit issuance integration (W1625.5)
- **Custody & precedence** (per the [Event Custody & Precedence Register](../event-custody-and-precedence-register.md), E-09): no-receipt approval tiers consolidate here; the cross-store variant (higher fraud risk, Store Manager approval above PHP 5,000) runs VS-07 W12; POS tender mechanics per VS-08 W1538


### Pain Points / Risks
- **Refund-fraud risk**: no-receipt returns (~8,000–10,000/month) attract serial abuse; mitigated by government-ID recording, a per-customer no-receipt counter with hard limits, and store-credit-only refunds (steps 3–4)
- **Over-valuation risk**: no-receipt credit at current price over-refunds items bought on promotion; mitigated by lowest-recent-price credit policy with supervisor approval tiers (step 3)

### Automation Opportunity
- System auto-scan of "scan loyalty card if customer is a member" (replaces manual Step 1).
- System auto-record of "recorded in system for fraud tracking" (replaces manual Step 3).
- System auto-count of "System records no-receipt return against customer ID" (replaces manual Step 4).

### Controls
- CTL-179 (ensure returns integrity & refund-fraud prevention.)
- operational: standard operating procedures; system-enforced validation rules

### Time Estimate
~10 min per no-receipt return (transaction lookup 3 min + verification and processing 5 min + store-credit issuance 2 min; recording against customer ID automated) × ~8,000–10,000/month ≈ 16,000–20,000 hours/year of CSR time (~45–50 per store/month).

| Field | Detail |

### Steps

### System Touchpoints
- Return condition flag with routing to Department Supervisor (W1626.1)
- Disposition decision with inventory status update (W1626.2–3)
- Quarantine aging report (W1626.4)


### Pain Points / Risks
- **Mis-disposition risk**: items restocked with missing accessories or damage leak value at full price; mitigated by the Department Supervisor assessment matrix (resaleable / markdown / damaged-defective / quarantine) instead of default restock (step 2)
- **Quarantine-aging risk**: disposition limbo ties up stock and vendor claim windows; mitigated by weekly Store Manager review of items in quarantine >7 days with Buyer escalation (step 4)

### Automation Opportunity
- System auto-route of "routes to Department Supervisor for quality assessment instead of immediate…" (replaces manual Step 1).
- System auto-count of "Department Supervisor assesses returned item" (replaces manual Step 2).
- System auto-update of "updates inventory status based on disposition" (replaces manual Step 3).

### Controls
- CTL-337 (ensure controlled execution — Customer Returns Processing (PA-32.1).)
- operational: Department Supervisor review and approval gate

### Time Estimate
~7 min per assessed return (condition flagging 2 min + supervisor assessment 5 min; inventory status updates automated) × ~8,000–10,000/month ≈ 11,200–14,000 hours/year; weekly quarantine review 30 min/store ≈ 5,200 hours/year across 200 stores.

## W1628. Customer Return Trend Analysis & Fraud Detection

| Field | Detail |
|---|---|
| **Trigger** | Monthly returns analysis cycle or real-time fraud alert |
| **Frequency** | Monthly trend analysis; real-time fraud monitoring |
| **Volume** | ~56,000 returns/month across 200 stores |
| **Owner** | Loss Prevention Manager |
| **Participants** | Loss Prevention Manager, Store Managers, Customer Service Manager, Finance |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | System continuously monitors return patterns for fraud indicators: (a) same customer > 5 returns in 30 days, (b) no-receipt returns > 3 per customer in 6 months, (c) returns of high-value items without original packaging, (d) return rate by store > 3% (flag vs. chain average ~2%), (e) returns processed by same CSR with high frequency (> 20% of store returns), (f) price difference between original purchase and return credit (switch fraud — buy on sale, return at full price using old receipt) | System | Loss Prevention Manager | Automated |
| 2 | Real-time alerts: system sends fraud alert to Loss Prevention Manager and Store Manager for flagged transactions; Store Manager has authority to deny return if fraud suspected | System | Store Manager | Immediate |
| 3 | Monthly: Loss Prevention Manager generates Returns Analytics Report: (a) return rate by store, by category, by reason code, (b) return rate trend (monthly, quarterly, YoY), (c) top 20 items by return volume, (d) top 20 customers by return frequency, (e) return fraud cases detected and resolved, (f) financial impact of returns (revenue reversal, handling cost, markdown cost) | Loss Prevention Manager | VP Store Operations | 4 hours/month |
| 4 | Monthly: Category Manager reviews top 20 items by return volume; identifies root causes: (a) quality issue → vendor VCAR (W1610), (b) product description mismatch → update product information (W50), (c) sizing confusion → update labeling and store signage, (d) packaging damage → improve packaging or handling procedure | Category Manager | VP Merchandising | 2 hours/month |

### System Touchpoints
- Real-time return fraud detection rules engine (W1628.1)
- Alert notification to Loss Prevention and Store Manager (W1628.2)
- Returns analytics dashboard with multi-dimensional analysis (W1628.3)
- Integration with vendor quality (W1610) and product content (W50) workflows (W1628.4)


### Pain Points / Risks
- **Threshold-gaming risk**: serial returners stay just under the >5-returns-in-30-days tripwires; mitigated by layered pattern rules with real-time alerts and Store Manager authority to deny on suspicion (steps 1–2)
- **Root-cause-blindness risk**: high return rates accepted as cost-of-doing-business; mitigated by monthly analytics routing the top-20 return items to vendor VCARs (W1610) or product-description corrections (step 4)

### Automation Opportunity
- System auto-monitor of "monitors return patterns for fraud indicators" (replaces manual Step 1).
- System auto-send of "sends fraud alert to Loss Prevention Manager and Store Manager for flagged…" (replaces manual Step 2).
- System auto-generate of "generates Returns Analytics Report" (replaces manual Step 3).

### Controls
- CTL-179 (ensure returns integrity & refund-fraud prevention.)
- operational: Loss Prevention Manager review and approval gate

### Time Estimate
Monthly analytics cycle 6 hours (LP Returns Analytics Report 4 hours + Category top-20 return-item review 2 hours) ≈ 72 hours/year across ~56,000 returns/month (fraud-pattern monitoring and alerts automated/real-time).

- AR credit note register and analytics (W1629.6)


### Pain Points / Risks
- **Compliance risk**: B2B return credits issued without a credit note referencing the original invoice create BIR exposure; mitigated by invoice-validated Return Authorization and credit notes tied to the original sales invoice (steps 2–4)
- **Speculative-order abuse risk**: trade customers use returns to unwind over-ordered speculative buys; mitigated by Sales Manager reason assessment with restocking-fee application per policy (step 2)

### Automation Opportunity
- System workflow notification of "contacts Sales Manager or Customer Service to request return" (replaces manual Step 1).
- System auto-review of "reviews return request" (replaces manual Step 2).
- System auto-create of "creates Return Authorization in system" (replaces manual Step 3).

### Controls
- CTL-337 (ensure controlled execution — Customer Returns Processing (PA-32.1).)
- operational: AR Clerk review and approval gate

### Time Estimate
~55 min per B2B return (request intake 10 min + Sales Manager review 15 min + approval/RA creation 10 min + goods-receipt verification 15 min + credit-note processing 5 min) × ~500–700 B2B returns/month ≈ 5,500–7,700 hours/year; monthly credit-note register review 1 hour ≈ 12 hours/year (credit-note generation automated).

## W1630. Customer Warranty Claim Processing & Vendor Claim Initiation

| Field | Detail |
|---|---|
| **Trigger** | Customer reports product failure within warranty period; or warranty claim registered at POS per POS-019 |
| **Frequency** | ~2,000–3,000 warranty claims/month |
| **Volume** | ~10–15 per store/month; highest for power tools and appliances |
| **Owner** | Customer Service Manager |
| **Participants** | CSR, Customer Service Manager, Department Supervisor, Buyer, vendor service center |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | Customer presents product with warranty claim at customer service counter: (a) CSR looks up original purchase transaction (receipt, loyalty card, or transaction number), (b) verifies warranty eligibility: (i) within warranty period (power tools: 6–12 months; appliances: 12–24 months per manufacturer), (ii) warranty covers reported failure type (manufacturing defect; excludes misuse, accidental damage, normal wear), (c) inspects product for misuse indicators (water damage on power tool, impact damage on appliance) | CSR | Customer Service Manager | 10 min |
| 2 | CSR creates warranty claim in system: (a) records product details, failure description, purchase date, warranty period, (b) attaches photos of product and defect, (c) classifies claim type: (i) **Repair** — product can be repaired at vendor service center, (ii) **Replacement** — product is beyond repair; vendor provides replacement unit, (iii) **Refund** — product is discontinued and no replacement available; process refund per W1627 | CSR | — | 5 min |
| 3 | **Repair path**: (a) system generates shipping label to vendor service center, (b) customer leaves product at store, (c) store consolidates warranty repair shipments weekly (sent to vendor service center), (d) vendor repairs and returns to store, (e) CSR notifies customer to pick up repaired product, (f) SLA: repair turnaround 14–21 business days | CSR / Buyer | Customer Service Manager | 5 min + waiting |
| 4 | **Replacement path**: (a) system checks replacement inventory at store; if available, immediate exchange per W1624, (b) if not available: Buyer contacts vendor for replacement unit; customer offered store credit (per W1627) or wait for replacement, (c) replacement unit received from vendor: CSR notifies customer for pickup | CSR / Buyer | Customer Service Manager | 5 min + waiting |
| 5 | **Vendor recovery**: (a) Buyer files warranty claim with vendor for all warranty repairs/replacements, (b) tracks vendor warranty claim status and recovery amount, (c) vendor provides: repair at no cost, replacement unit at no cost, or credit note, (d) unrecovered warranty costs tracked per vendor as quality cost per W1614 | Buyer | Category Manager | 30 min/week |
| 6 | Monthly: Customer Service Manager generates warranty claim report: (a) claims by product category and vendor, (b) claim rate as % of sales by SKU, (c) average turnaround time by vendor, (d) customer satisfaction with warranty process, (e) feeds into vendor quality scorecard per W1608 | Customer Service Manager | VP Store Operations | 2 hours/month |

### System Touchpoints
- Purchase transaction lookup with warranty eligibility check (W1630.1)
- Warranty claim creation with photo attachment and classification (W1630.2)
- Vendor service center shipping integration (W1630.3)
- Replacement inventory check and exchange processing (W1630.4)
- Vendor warranty claim tracking (W1630.5)
- Warranty claim analytics dashboard (W1630.6)


### Pain Points / Risks
- **Warranty-theft risk**: claims on out-of-warranty or never-purchased products; mitigated by purchase-transaction lookup and warranty-period validation before claim creation (step 1)
- **Vendor-recovery leakage risk**: store-level warranty repairs and replacements never claimed back to the vendor; mitigated by vendor claim initiation built into the repair/replacement paths (steps 3–4)

### Automation Opportunity
- System auto-inspect of "inspects product for misuse indicators" (replaces manual Step 1).
- System auto-capture of "creates warranty claim in system" (replaces manual Step 2).
- System auto-generate of "generates shipping label to vendor service center" (replaces manual Step 3).

### Controls
- CTL-179 (ensure returns integrity & refund-fraud prevention.)
- operational: standard operating procedures; system-enforced validation rules

### Time Estimate
~20–25 min per warranty claim (product lookup 10 min + claim creation 5 min + repair/replacement path handling 5 min; vendor-side service waits excluded) × ~2,000–3,000 claims/month ≈ 8,000–15,000 hours/year of CSR time; vendor recovery filings 30 min/week ≈ 26 hours/year; monthly claims report 2 hours ≈ 24 hours/year.
