## W883. Ad-hoc Analytics Request Fulfillment & SLA Management

| Field | Detail |
|---|---|
| **Trigger** | Business user submits analytics request that cannot be answered by existing dashboards or reports |
| **Frequency** | ~30–50 ad-hoc requests per month |
| **Volume** | Average request: 4–8 hours to fulfill; complex requests: 20–40 hours |
| **Owner** | BI Analyst / BI Manager |
| **Participants** | Business Requestor, BI Analyst, Data Engineer (for complex data extraction), BI Manager |

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | Receive and triage request — log request in analytics queue: (a) business question, (b) urgency (standard: 5 business days, urgent: 2 business days, executive: same day), (c) data requirements, (d) output format (report, visualization, data extract, presentation); assign to BI Analyst based on expertise and workload | BI Manager | BI Analyst | 15 min |
| 2 | Clarify requirements — BI Analyst meets with requestor to: (a) understand decision context and how analysis will be used, (b) define scope (time period, geography, product categories), (c) agree on methodology and output format, (d) set delivery timeline | BI Analyst | BI Manager | 30 min |
| 3 | Extract and prepare data — (a) identify data sources, (b) build SQL queries or ETL pipeline, (c) validate data quality and completeness, (d) transform data for analysis | BI Analyst | Data Engineer | 1–4 hours |
| 4 | Conduct analysis — apply appropriate methods: (a) descriptive statistics and trend analysis, (b) comparison (same-store, year-over-year, plan vs. actual), (c) segmentation (customer, product, geography), (d) correlation analysis (if applicable); document methodology and assumptions | BI Analyst | BI Manager | 2–8 hours |
| 5 | Create deliverable — prepare output: (a) executive summary with key findings, (b) supporting visualizations, (c) data tables with source notes, (d) methodology documentation, (e) limitations and caveats; format per request (PDF, PPT, interactive dashboard, Excel) | BI Analyst | BI Manager | 1–4 hours |
| 6 | Review and deliver — BI Manager reviews for accuracy and clarity; requestor reviews for completeness; iterate if needed; deliver final output | BI Manager | Business Requestor | 30 min |
| 7 | Evaluate for reusability — if request is recurring: propose dashboard or automated report development (per W880); add to development backlog with priority ranking | BI Analyst | BI Manager | 15 min |

- **BI Platform** — ad-hoc query tool, visualization development
- **Data Warehouse** — data extraction, SQL analysis

- Output may be misinterpreted — clear caveats and methodology documentation required

## W1178. Predictive Analytics Model Development, Deployment & Monitoring

| Field | Detail |
|---|---|
| **Trigger** | Business need for predictive capability; or annual analytics roadmap planning; or pilot success triggering production deployment |
| **Frequency** | ~4–6 new model development projects per year; continuous monitoring of production models |
| **Volume** | 3–5 production models in operation at any time; serving 200 stores and 4 DCs |
| **Owner** | Data Scientist / BI Manager |
| **Participants** | Data Scientist, BI Manager, Business Domain Owner (Category Manager, VP Supply Chain, CHRO), Data Engineer, IT Operations |

### Background

BuildRight's 33.6M annual transactions, 35,000 active SKUs, 200 stores, and ~800 vendors generate rich data sets suitable for predictive analytics. Key use cases for a big-box home improvement retailer include: (a) **Demand sensing**: improve forecast accuracy beyond W31 statistical forecasting by incorporating weather data (PAGASA), local events (fiestas, construction booms), and social media signals; (b) **Customer churn prediction**: identify loyalty members per W17 at risk of lapsing and trigger targeted retention per W660; (c) **Inventory risk scoring**: predict which SKUs are likely to become slow-moving or obsolete per W587, enabling proactive markdown; (d) **Vendor reliability prediction**: forecast which vendors are likely to miss OTIF targets per W44, enabling proactive sourcing alternatives; (e) **Store performance prediction**: identify stores likely to miss quarterly revenue targets, enabling early intervention. This workflow governs the lifecycle of predictive models from ideation through deployment and monitoring.

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | **Use case identification & prioritization**: Annual planning + ad-hoc: (a) BI Manager and business domain owners identify predictive analytics use cases; (b) score each use case on: business impact (revenue, cost, risk), data availability and quality, technical feasibility, and implementation effort; (c) prioritize top 4–6 use cases for annual roadmap; (d) CIO approves roadmap and budget; (e) quick wins (high impact, low effort) scheduled for H1 | BI Manager / Business Domain Owner | CIO | 2 days |
| 2 | **Data exploration & preparation**: For each approved use case: (a) Data Scientist explores available data: historical sales (POS), inventory movements, customer transactions, vendor performance, weather, economic indicators; (b) assess data quality per W1177 governance standards; (c) build feature engineering pipeline: derive predictive variables (lagged sales, rolling averages, seasonality indicators, store demographic features); (d) prepare training data set with appropriate time splits; (e) document data sources, transformations, and assumptions | Data Scientist / Data Engineer | BI Manager | 2–4 weeks |
| 3 | **Model development & validation**: (a) Data Scientist trains multiple model types: time series (ARIMA, Prophet), regression (XGBoost, LightGBM), neural networks (for complex patterns); (b) cross-validate using walk-forward validation for time series; (c) compare model performance vs. baseline (current W31 forecast, random baseline, naive seasonal baseline); (d) select best model based on: accuracy (MAPE, RMSE), interpretability, computational cost, robustness; (e) document model architecture, hyperparameters, and performance metrics; (f) Business Domain Owner reviews model logic for business plausibility | Data Scientist | BI Manager | 2–6 weeks |
| 4 | **Pilot deployment**: (a) deploy model in pilot scope: 1–2 product categories for demand sensing, or 1 region for churn prediction; (b) run model alongside existing process for 4–8 weeks; (c) compare model predictions to actual outcomes; (d) measure business impact: forecast accuracy improvement, churn reduction, inventory risk identification lead time; (e) iterate on model based on pilot findings; (f) Business Domain Owner approves for production based on pilot results | Data Scientist / Data Engineer / BI Manager | Business Domain Owner | 4–8 weeks |
| 5 | **Production deployment**: (a) Data Engineer integrates model into production data pipeline: scheduled batch scoring (nightly for demand sensing, weekly for churn, monthly for inventory risk); (b) IT Operations deploys model infrastructure (cloud compute, API endpoints); (c) integrate model outputs into existing workflows: demand forecast feed to W31 S&OP, churn scores to W660 retention program, inventory risk scores to W587 obsolescence review; (d) build monitoring dashboard showing model predictions, accuracy, and drift metrics | Data Engineer / IT Operations | BI Manager | 2–4 weeks |
| 6 | **Ongoing model monitoring**: Continuous monitoring: (a) **Prediction accuracy**: track MAPE/RMSE weekly; alert if accuracy degrades > 20% from baseline; (b) **Data drift**: monitor input feature distributions for shifts (e.g., sales pattern change after new competitor enters market); (c) **Concept drift**: monitor if relationship between features and target changes (e.g., economic downturn changes price sensitivity); (d) **Business KPI impact**: track if model-driven decisions actually improve business outcomes; (e) monthly model health report to BI Manager | Data Scientist / System | BI Manager | 2 hours/week |
| 7 | **Model retraining & retirement**: (a) quarterly: retrain models with latest data to incorporate new patterns; (b) if retrained model significantly outperforms production model: promote to production; (c) if model consistently underperforms baseline: retire model and revert to existing process; (d) document model version history and performance trajectory | Data Scientist | BI Manager | 1 day/quarter |

### System Touchpoints
- Data warehouse per W881 for training data extraction
- ML platform (cloud-based: AWS SageMaker, Azure ML, or GCP Vertex AI) for model training, deployment, and monitoring
- Feature store for reusable predictive variables
- Integration with W31 demand forecasting, W660 retention, W587 obsolescence, W44 vendor scorecard
- Model monitoring dashboard with drift detection
- BI platform for presenting model insights to business users

### Pain Points / Risks
- **Data quality dependency**: models are only as good as their training data; data quality issues per W884 directly impact model accuracy; demand sensing for provincial stores may be unreliable due to sparse transaction data
- **Black box perception**: business users may distrust model recommendations they don't understand; interpretability features (SHAP values, feature importance) essential for adoption
- **Overfitting risk**: complex models may fit historical patterns that don't repeat; walk-forward validation mitigates but doesn't eliminate
- **Change management**: replacing intuitive merchandising decisions with model-driven recommendations requires cultural shift; Category Manager buy-in critical
- **Computational cost**: production models require cloud compute resources; monthly cost can reach PHP 200,000–500,000 for complex models at BuildRight's scale


### Automation Opportunity
- System auto-schedule of "scheduled for H1" (replaces manual Step 1).
- System auto-document of "document data sources, transformations, and assumptions" (replaces manual Step 2).
- System auto-log of "logic for business plausibility" (replaces manual Step 3).

### Controls
- CTL-327 (ensure controlled execution — Advanced Analytics (PA-28.3).)
- operational: Data Scientist / BI Manager review and approval gate

### Staffing Implication
- **Data Scientist**: 1 FTE dedicated to predictive analytics development and monitoring; ~80% of time on model lifecycle
- **Data Engineer**: model deployment and pipeline integration ~20% of time; absorbed by existing role
- **BI Manager**: use case prioritization and business stakeholder management ~10% of time; absorbed by existing role

### Time Estimate
- Per model: ideation 1 day + data prep 2–4 weeks + development 2–6 weeks + pilot 4–8 weeks + production 2–4 weeks = **3–6 months**
- Ongoing monitoring: 2 hours/week per production model
- Quarterly retraining: 1 day/model
- **Annual estimate: ~2,000–3,000 hours/year for 4–6 model projects + monitoring**

## W1215. Customer Segmentation & Basket Analysis for Category Management

| Field | Detail |
|---|---|
| **Trigger** | Quarterly category management review cycle; or triggered by Category Manager request for new product introduction decision; or annual customer segmentation refresh |
| **Frequency** | Quarterly analysis deliverables; annual full segmentation refresh |
| **Volume** | ~600,000 loyalty members + ~5,200 trade accounts segmented; 33.6M annual transactions analyzed for basket patterns |
| **Owner** | BI Analyst / Category Manager |
| **Participants** | BI Analyst, Category Manager, Loyalty Program Manager, VP Merchandising, Ecommerce Manager |

### Background

BuildRight Depot serves diverse customer segments (DIY homeowners, trade professionals, corporate/institutional buyers, ecommerce shoppers) with a 35,000 SKU assortment. Understanding what different customer segments buy, how products are combined in baskets, and how purchasing behavior varies by segment is critical for assortment optimization, promotional targeting, and store layout decisions. Key questions this workflow answers: (a) Which SKUs are most frequently purchased together (affinity analysis)?, (b) What is the basket composition difference between trade professionals and DIY homeowners?, (c) Which customer segments drive the highest margin?, (d) What cross-sell opportunities exist (customers who buy tiles also buy...)?, (e) How does ecommerce basket behavior differ from in-store? This analysis directly feeds category management decisions (SKU rationalization, promotional planning, planogram optimization) and loyalty program personalization.

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | **Data preparation** (quarterly): BI Analyst extracts transaction data from data warehouse: (a) all POS and ecommerce transactions for the quarter, (b) linked customer identifiers (loyalty card, trade account, guest), (c) item-level detail with category hierarchy, (d) transaction metadata (store, date/time, channel, payment method), (e) customer master attributes (segment, tenure, location, tier) | BI Analyst | BI Manager | 4–8 hours |
| 2 | **Customer segmentation refresh** (annual): BI Analyst refreshes customer segmentation model using RFM (Recency, Frequency, Monetary) analysis + category affinity: (a) calculate RFM scores for each customer, (b) cluster customers into segments: (i) Trade Loyalists (high frequency, high value, trade account), (ii) Weekend Warriors (moderate frequency, DIY categories, weekends), (iii) Project Planners (low frequency, high value per trip, project-oriented purchases), (iv) Convenience Shoppers (high frequency, low value, proximity-driven), (v) Digital Natives (ecommerce-primary, younger demographic), (vi) Lapsed Customers (no purchase in 90+ days); (c) validate segments with Category Managers for business plausibility; (d) publish segment assignments to CRM for campaign targeting | BI Analyst / Category Manager | VP Merchandising | 1–2 weeks (annual) |
| 3 | **Basket analysis** (quarterly): BI Analyst conducts market basket analysis on quarterly transaction data: (a) **Affinity analysis**: identify SKU pairs/groups with high co-occurrence (lift > 1.5) — e.g., tiles + tile adhesive + grout, aircon + copper tubing + electrical wire; (b) **Category adjacency**: which categories are bought together in same trip?; (c) **Sequential purchasing**: items bought in repeat visits within 30 days (project phased purchasing); (d) **Channel comparison**: in-store vs. ecommerce basket size, composition, and cross-sell patterns; (e) **Trade vs. DIY**: basket profile comparison between trade accounts and walk-in customers | BI Analyst | Category Manager | 1–2 weeks |
| 4 | **Segment profitability analysis** (quarterly): BI Analyst calculates contribution by segment: (a) revenue and gross margin by customer segment, (b) average basket size and margin by segment, (c) cost-to-serve by segment (trade accounts require credit management per W24; ecommerce requires fulfillment cost; walk-in requires store staffing), (d) lifetime value estimation for each segment | BI Analyst | VP Merchandising | 3–5 days |
| 5 | **Category management insights delivery**: BI Analyst presents findings to Category Managers: (a) **Cross-sell opportunities**: "Customers who bought X also bought Y" for display pairing, bundle creation per W1, and POS suggestive selling per W748; (b) **SKU rationalization**: identify SKUs with zero cross-sell value and low standalone sales — candidates for discontinuation; (c) **Assortment gaps**: customer segments purchasing categories outside BuildRight (identified from loyalty survey data) — opportunity for new product introduction; (d) **Planogram insights**: high-affinity categories should be co-located in store layout per W86; (e) **Promotional targeting**: segment-specific promotion recommendations (e.g., Trade Loyalists respond to bulk discounts; Weekend Warriors respond to bundle deals) | BI Analyst / Category Manager | VP Merchandising | 2–3 hours per category |
| 6 | **Loyalty program personalization**: Loyalty Program Manager uses segmentation to: (a) configure segment-specific earning rules per W496 (e.g., double points on paint category for Weekend Warriors), (b) create targeted campaign lists per W300 (e.g., "Project Planner" segment receives project completion reminder emails), (c) personalize in-app product recommendations based on segment and basket affinity | Loyalty Program Manager | VP Marketing | 1 day/quarter |
| 7 | Category Manager documents decisions and actions taken based on analysis; tracks impact on subsequent quarter's metrics (did cross-sell rate improve? did targeted promotions lift revenue?) | Category Manager | VP Merchandising | Ongoing |

### System Touchpoints
- Data warehouse per W881: transaction data, customer master, item hierarchy
- BI analytics platform: clustering algorithms (k-means for segmentation), association rules (apriori algorithm for basket analysis), RFM scoring
- CRM integration: segment assignments synced to customer profiles for campaign targeting
- Category management module: assortment planning, SKU rationalization
- Loyalty engine: segment-specific earning rules and promotion targeting
- Integration with W1 (assortment planning), W86 (planogram), W300 (campaign management), W496 (loyalty rules), W748 (POS upselling), W885 (executive reporting)

### Pain Points / Risks
- **Guest transaction gap** — ~45% of in-store transactions are non-loyalty guest purchases; these transactions are invisible for customer-level segmentation; only aggregated category analysis possible
- **Segment model decay** — customer behavior shifts over time; annual refresh may miss emerging segments (e.g., post-pandemic DIY boom); semi-annual refresh recommended for high-volatility periods
- **Actionability gap** — sophisticated analysis that Category Managers don't act on is wasted; close collaboration between BI Analyst and Category Managers during analysis ensures business relevance
- **Data warehouse performance** — basket analysis on 33.6M annual transactions requires significant compute; quarterly batch processing mitigates performance impact on operational systems


### Automation Opportunity
- System auto-count of "account, guest" (replaces manual Step 1).
- System auto-validate of "validate segments with Category Managers for business plausibility" (replaces manual Step 2).
- System auto-file of "profile comparison between trade accounts and walk-in customers" (replaces manual Step 3).

### Controls
- CTL-327 (ensure controlled execution — Advanced Analytics (PA-28.3).)
- operational: standard operating procedures; system-enforced validation rules

### Staffing Implication
- BI Analyst: ~80 hours/quarter for basket analysis and segment refresh; absorbed by existing BI team
- Category Managers: ~4–6 hours/quarter for insights review and action planning (5 Category Managers)
- Loyalty Program Manager: ~8 hours/quarter for personalization configuration
- No incremental headcount

### Time Estimate
- Quarterly basket analysis: ~40–60 hours BI Analyst time
- Annual segmentation refresh: ~40–80 hours BI Analyst time
- Category review sessions: 5 categories × 2–3 hours = 10–15 hours
- Loyalty personalization: ~8 hours/quarter
- **Annual estimate: ~240–370 hours for BI analysis (per the components above) + ~80 hours for business review and action**

## W1251. Category Space Productivity Analytics & Planogram Performance Measurement

| Field | Detail |
|---|---|
| **Trigger** | Scheduled — monthly category space productivity report; quarterly planogram compliance audit; ad-hoc triggered by category margin decline or planogram refresh request |
| **Frequency** | Monthly analytics; quarterly planogram compliance measurement; ad-hoc for new planogram validation |
| **Volume** | 35,000 active SKUs across 200 stores × 12 product categories; quarterly planogram audit for ~50 high-priority planograms |
| **Owner** | BI Analyst (Space & Category Analytics) |
| **Participants** | Category Manager, Merchandising Planner, VP Store Operations, VP Merchandising |

### Background

BuildRight Depot carries 35,000 active SKUs across 8,000–15,000 sqm selling areas in 200 stores, averaging 2.3–4.4 SKUs per sqm. Each product category competes for finite shelf and display space, and the productivity of that space directly impacts revenue and margin performance. Despite the scale, systematic measurement of space productivity — revenue per sqm by category, planogram compliance rates, and fixture performance — is not fully operationalized. This workflow establishes the analytics framework for: (a) measuring category space productivity (sales per sqm, margin per sqm, GMROI by fixture); (b) validating planogram performance (planned vs. actual sales lift after planogram change); (c) identifying underperforming space allocation for optimization; (d) feeding data into merchandising decisions for assortment rationalization and space reallocation.

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | **Monthly category space productivity report**: BI Analyst generates monthly report per category: (a) sales per sqm by category (using planogram fixture dimensions from space planning module); (b) gross margin per sqm by category; (c) GMROI (Gross Margin Return on Inventory Investment) per category; (d) inventory turns per category; (e) compare category productivity to national average and regional benchmarks; (f) flag categories where sales per sqm declined > 5% month-over-month | BI Analyst | Category Manager | 4 hours/month |
| 2 | **Planogram compliance measurement**: Using planogram audit data from store visits (W86) and digital planogram compliance tools: (a) measure compliance rate — % of stores with correct planogram execution by category; (b) correlate compliance rate with sales performance — do high-compliance stores outperform low-compliance stores? (c) identify planograms with < 80% compliance rate for corrective action; (d) report compliance by region — provincial stores typically have lower compliance than Metro Manila stores | BI Analyst | VP Merchandising | 4 hours/month |
| 3 | **Planogram sales lift validation**: After planogram refresh (new planogram deployed): (a) measure 4-week and 8-week sales performance vs. pre-planogram baseline; (b) isolate planogram effect from promotional and seasonal effects; (c) calculate incremental sales per sqm from planogram change; (d) compute ROI of planogram investment (labor cost for reset vs. incremental margin); (e) validate or refute planogram hypothesis — share results with Category Manager | BI Analyst | Category Manager | 4 hours per planogram validation |
| 4 | **Underperforming space identification**: Quarterly analysis to identify space reallocation opportunities: (a) rank all categories by sales per sqm; (b) identify categories where space allocation exceeds productivity contribution (e.g., 14% of space but 6% of sales); (c) identify high-productivity categories constrained by insufficient space; (d) model space reallocation scenarios — what would happen if 50 sqm moved from Garden to Power Tools?; (e) present recommendations to VP Merchandising for annual planogram rebalancing | BI Analyst / Merchandising Planner | VP Merchandising | 8 hours/quarter |

### System Touchpoints
- **Space Planning Module** — planogram definitions, fixture dimensions, shelf allocations
- **POS System** — sales data by category, SKU, and store
- **Inventory Module** — on-hand quantities, inventory value by category
- **BI Platform** — space productivity dashboards, planogram compliance analytics
- **Planogram Compliance Tool** — digital audit capture, compliance scoring

### Pain Points / Risks
- Accurate fixture dimension data is required for space calculations — may not exist for all 200 stores, especially older stores with non-standard fixtures
- Planogram compliance measurement relies on store visit audits — limited to sample-based measurement unless digital compliance tools are deployed
- Seasonal fluctuations distort monthly space productivity (e.g., garden category peaks in summer)
- Space reallocation decisions have long lead times (planogram redesign, fixture procurement, store reset labor) — analytics must be timely


### Automation Opportunity
- System auto-generate of "generates monthly report per category" (replaces manual Step 1).
- System auto-report of "than Metro Manila stores" (replaces manual Step 2).
- System auto-validate of "validate or refute planogram hypothesis — share results with Category Manager" (replaces manual Step 3).

### Controls
- CTL-327 (ensure controlled execution — Advanced Analytics (PA-28.3).)
- operational: standard operating procedures; system-enforced validation rules

### Staffing Implication
- 1 BI Analyst dedicated to space and category analytics
- Merchandising Planner: 4 hours/month reviewing space productivity data
- Category Managers: 2 hours/month reviewing their category's space performance

### Time Estimate
- Monthly reporting: 8 hours/month (Steps 1+2) = 96 hours/year
- Quarterly analysis: 8 hours/quarter = 32 hours/year
- Planogram validations: 4 hours × 50 planograms/year = 200 hours/year

## W1252. Supply Chain Predictive Analytics, Demand Sensing & Early Warning System

| Field | Detail |
|---|---|
| **Trigger** | Scheduled — weekly demand sensing refresh; monthly model retraining; ad-hoc triggered by supply chain disruption alert or forecast accuracy degradation |
| **Frequency** | Weekly demand sensing update; monthly model performance review; quarterly model recalibration |
| **Volume** | 35,000 active SKUs across ~205 locations (200 stores + 4 DCs); weekly demand signal processing for all A-class and B-class SKUs (~17,500 SKUs) |
| **Owner** | Data Scientist / Supply Chain Analyst |
| **Participants** | Demand Planner, Category Manager, Import Coordinator, Logistics Planner, VP Supply Chain |

### Background

BuildRight Depot's supply chain faces unique Philippine challenges: (a) island geography creates multi-modal logistics (truck, RoRo ferry, inter-island vessel) with 2–5 day transit variability; (b) 40% of COGS comes from imports with 45–90 day lead times requiring long-range demand visibility; (c) typhoon season (June–November) disrupts both inbound logistics and store-level demand patterns unpredictably; (d) regional economic cycles (construction booms in developing provinces) create localized demand spikes not captured by national-level forecasting. Traditional time-series forecasting (per W31) captures seasonal patterns but cannot detect emerging demand shifts early enough for import ordering decisions. This workflow operationalizes predictive analytics and demand sensing: using machine learning models that incorporate external signals (weather forecasts, construction permit data, social media trending, commodity price movements) to generate early warnings of demand shifts 4–12 weeks before they appear in traditional forecast data.

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | **Weekly demand sensing refresh**: Data Scientist runs weekly demand sensing pipeline: (a) ingest external data feeds: PAGASA weather forecast, DOLE construction permit releases, cement/steel commodity price indices, social media trend signals for home improvement topics; (b) ML model generates adjusted demand forecast for next 12 weeks by SKU-location; (c) compare model forecast to current statistical forecast (W31) — flag SKUs where demand sensing forecast deviates > 15%; (d) generate demand shift alerts: (i) emerging demand spike (construction activity uptick in a region), (ii) demand collapse (typhoon approaching — demand drops pre-landfall then spikes for emergency supplies), (iii) commodity price-driven substitution (steel price increase drives shift from rebar to alternative framing) | Data Scientist | VP Supply Chain | 4 hours/week |
| 2 | **Alert triage & action**: Demand Planner reviews demand sensing alerts: (a) validate top 20 alerts against market intelligence — are they real signals or noise?; (b) for validated demand spikes: check current on-hand, in-transit, and open PO coverage — is there sufficient stock to capture the demand?; (c) for validated demand collapses: review open import POs — should any be deferred or cancelled to avoid overstock?; (d) generate recommended actions: expedite PO, allocate safety stock increase, adjust replenishment parameters per W312; (e) escalate to Import Coordinator for PO action on import items | Demand Planner | VP Supply Chain | 3 hours/week |
| 3 | **Monthly model performance review**: Data Scientist evaluates predictive model accuracy: (a) calculate MAPE (Mean Absolute Percentage Error) for demand sensing forecast vs. actual sales for past 4 weeks; (b) compare demand sensing MAPE to traditional forecast MAPE — is the ML model adding value?; (c) analyze false positive rate — how many alerts were validated vs. rejected?; (d) identify SKUs or locations where model performs poorly — feature engineering or data quality issues; (e) document model performance in monthly MLOps report | Data Scientist | VP Supply Chain | 4 hours/month |
| 4 | **Quarterly model recalibration**: Retrain and recalibrate ML models: (a) update training data with latest 12 months of actual sales; (b) evaluate new external data sources (e.g., satellite imagery for construction activity, Google Trends data for DIY interest); (c) tune hyperparameters for improved accuracy; (d) A/B test recalibrated model vs. current model for 2 weeks; (e) deploy updated model if accuracy improvement > 5% MAPE reduction | Data Scientist | VP Supply Chain | 16 hours/quarter |
| 5 | **Early warning escalation**: For critical supply chain disruptions (typhoon forecast, port congestion, political instability in import sourcing countries): (a) generate emergency demand impact assessment for all affected locations; (b) model stock-out risk for critical SKUs (cement, plywood, emergency supplies); (c) recommend pre-positioning actions — move inventory from low-risk DCs to high-risk regions; (d) brief VP Supply Chain and COO on recommended response | Data Scientist / Demand Planner | VP Supply Chain | 4 hours per event |

### System Touchpoints
- **ML/AI Platform** — demand sensing model training, inference, and monitoring
- **ERP Forecasting Module** — baseline statistical forecast (W31) for comparison
- **External Data Feeds** — PAGASA weather, construction permits, commodity prices, social media APIs
- **BI Platform** — demand sensing dashboard, alert visualization, model performance tracking
- **Supply Chain Module** — current on-hand, in-transit, open PO data for alert validation
- **Procurement Module** — PO action for expedite/defer recommendations

### Pain Points / Risks
- External data feed reliability is variable — PAGASA forecasts may be inaccurate beyond 5 days; construction permit data may have 30–60 day lag
- ML model requires 12+ months of clean historical data — new stores (< 1 year) cannot use demand sensing
- Demand sensing model interpretability — supply chain planners may distrust ML-generated alerts they cannot explain
- Over-reliance on predictive analytics may reduce planner intuition and market knowledge
- Cost of external data subscriptions may not justify marginal forecast improvement for C-class SKUs


### Automation Opportunity
- System auto-generate of "generates adjusted demand forecast for next 12 weeks by SKU-location" (replaces manual Step 1).
- System auto-review of "reviews demand sensing alerts" (replaces manual Step 2).
- System auto-document of "document model performance in monthly MLOps report" (replaces manual Step 3).

### Controls

## W1398. Customer Churn Prediction Model, At-Risk Account Identification & Proactive Retention Campaign

| Field | Detail |
|---|---|
| **Trigger** | Scheduled — monthly model scoring run; quarterly model performance review |
| **Frequency** | Monthly scoring (all active accounts); quarterly model review and retraining |
| **Volume** | ~5,400 trade and corporate accounts scored monthly; ~600K loyalty members scored quarterly |
| **Owner** | Senior Data Scientist |
| **Participants** | Senior Data Scientist, BI Manager, Credit Manager, Loyalty Manager, Head of Trade / Account Management |

### Background

BuildRight's trade and corporate accounts (~5,400) generate an estimated 25–30% of total revenue. Customer churn — trade accounts switching to competitors (CitiHardware, Wilcon, local independent hardware stores) or reducing purchase volume — directly impacts revenue and profitability. Acquiring a new trade account costs 5–7× more than retaining an existing one (sales rep effort, credit assessment, onboarding). Similarly, loyalty member churn (inactive members who stop shopping at BuildRight) erodes the loyalty program's value and future revenue predictability. This workflow deploys a machine learning churn prediction model that identifies at-risk customers before they leave, enabling proactive retention interventions.

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | **Monthly scoring run**: system executes churn prediction model against all active trade/corporate accounts: (a) model inputs: purchase frequency (transactions/month), purchase volume trend (3-month rolling average vs. 12-month average), average transaction value trend, category breadth (number of departments purchased from), days since last purchase, payment behavior (average days to pay, bounced checks per W1381), customer service interactions (complaints per W41, W13.1), competitive proximity (distance to nearest competitor store), account tenure, seasonal purchasing pattern; (b) model output: churn probability score (0–100%) for each account; (c) risk classification: High Risk (> 70% churn probability), Medium Risk (40–70%), Low Risk (< 40%) | System / Data Scientist | BI Manager | Automated (2–4 hours compute) |
| 2 | **At-risk account reporting**: system generates monthly churn risk report for Head of Trade / Account Management and Credit Manager: (a) High Risk accounts with key contributing factors (e.g., "purchase frequency declined 40% over 3 months", "no purchases in 45 days despite typical weekly purchasing"); (b) risk distribution: total revenue at risk by risk tier; (c) historical churn rate vs. predicted (model accuracy tracking); (d) recommended retention actions by risk tier | System | — | Automated |
| 3 | **Retention action — Trade accounts**: Head of Trade / Account Management assigns High Risk trade accounts to Sales Reps for proactive outreach: (a) Sales Rep contacts customer within 5 business days: understand reason for reduced purchasing (competitor offering better price/terms? customer project completed? customer dissatisfied with service?); (b) for price-sensitive customers: offer price match or volume discount per W922; (c) for service complaints: escalate to Store Manager or Operations for resolution; (d) for project customers between projects: maintain relationship through contractor events (W12.3) and promotional offers; (e) Sales Rep logs outreach outcome in CRM | Sales Rep / Head of Trade / Account Management | VP Commercial | 20–30 min/account |
| 4 | **Retention action — Loyalty members**: Loyalty Manager receives quarterly list of High Risk loyalty members: (a) design targeted retention campaign: personalized SMS/email with exclusive offer (double-points weekend, member-only discount coupon, early access to sale); (b) segment by churn driver: inactive members (no purchase in 60 days) vs. declining members (reduced frequency); (c) measure campaign effectiveness: reactivation rate (% of High Risk members who make a purchase within 30 days of campaign) | Loyalty Manager | CMO | Campaign-dependent |
| 5 | **Quarterly model performance review**: Senior Data Scientist evaluates model performance: (a) accuracy metrics: precision (what % of predicted churns actually churned?), recall (what % of actual churns did the model predict?), AUC-ROC curve; (b) feature importance: which factors are most predictive of churn?; (c) compare predicted vs. actual churn rate by risk tier; (d) if model performance degraded (AUC < 0.75 or precision < 60%), retrain model with updated data | Senior Data Scientist | BI Manager | 4–8 hours/quarter |
| 6 | **Annual model enhancement**: Senior Data Scientist evaluates new features and model improvements: (a) incorporate external data (construction industry index, regional building permit data as leading indicators); (b) test alternative algorithms (gradient boosting, neural networks vs. current logistic regression); (c) A/B test retention campaign effectiveness with and without model predictions; (d) present model ROI to BI Manager and VP Commercial: revenue retained through proactive outreach vs. cost of model development and retention campaigns | Senior Data Scientist | BI Manager | 20–30 hours/year |

### System Touchpoints
- Churn prediction model: ML model deployed on analytics platform, scoring active accounts monthly (W1398.1)
- Customer 360 view: integrated data from POS, CRM, AR, loyalty, and customer service for model feature computation (W1398.1)
- At-risk account dashboard: ranked list with risk score, contributing factors, and revenue-at-risk quantification (W1398.2)
- CRM integration: retention outreach logged per account with outcome tracking (W1398.3)
- Campaign management platform: targeted retention campaign creation, execution, and effectiveness measurement for loyalty members (W1398.4)
- Model performance monitoring: automated accuracy metrics computation with alerting on degradation (W1398.5)
- Integration with W17 (loyalty program), W13.3 (CRM), W572 (credit monitoring), W922 (bulk purchase negotiation), W1250 (foot traffic analytics), W1215 (customer segmentation)

### Pain Points / Risks
- **Model prediction lag**: the model detects churn risk based on historical purchasing patterns; by the time a trade account shows declining purchases, the customer may have already begun shifting purchases to a competitor; earlier signals (quote requests that don't convert, reduced store visits) could improve lead time but are harder to capture systematically
- **Retention action cost**: aggressive retention offers (discounts, extended payment terms) erode margin; the cost of retention must be weighed against the lifetime value of the customer; not all High Risk accounts are worth retaining at any cost
- **Model bias toward large accounts**: the model may be more accurate for large trade accounts (richer data history) than for small or occasional accounts; systematic under-prediction of churn in small accounts means the total revenue at risk is understated
- **Campaign fatigue**: loyalty members who receive too many "come back" offers may perceive them as spam; the retention campaign frequency must be calibrated to avoid damaging the brand relationship

## W1399. Store-Level Sales Forecasting Accuracy Monitoring, Model Drift Detection & Retraining Trigger

| Field | Detail |
|---|---|
| **Trigger** | Scheduled — monthly accuracy review; automated drift detection alerts |
| **Frequency** | Monthly accuracy monitoring; quarterly model drift assessment; retraining as triggered |
| **Volume** | 200 stores × 13 departments (~40 categories) = ~2,600 store-department forecasting units (up to ~8,000 at category grain) monitored monthly |
| **Owner** | Senior Data Scientist |
| **Participants** | Senior Data Scientist, BI Manager, Demand Planning Manager, VP Supply Chain |

### Background

BuildRight's demand forecasting model (W1206, W1252) generates store-level sales forecasts that drive replenishment orders (W4), inventory allocation, and supply planning (W2). Forecasting accuracy directly impacts inventory investment (overstock from inflated forecasts) and lost sales (stockouts from under-forecasting). With 200 stores × 13 departments (~40 categories) = ~2,600 forecasting units (up to ~8,000 at category grain), maintaining model accuracy at scale is challenging. Model drift — gradual degradation of forecast accuracy as purchasing patterns change (new competitors, economic shifts, seasonal pattern changes, promotional calendar changes) — must be detected and corrected through timely model retraining.

### Steps

| # | Activity | Role (R) | Role (A) | Duration |
|---|---|---|---|---|
| 1 | **Monthly accuracy computation**: system automatically computes forecast accuracy metrics for each store-department for the prior month: (a) MAPE (Mean Absolute Percentage Error): absolute(actual − forecast) ÷ actual × 100%; (b) WAPE (Weighted Absolute Percentage Error): weighted by revenue contribution; (c) Bias: systematic over-forecasting (positive bias) vs. under-forecasting (negative bias); (d) compute at store level, department level, and chain level | System | — | Automated |
| 2 | **Accuracy dashboard refresh**: system updates forecasting accuracy dashboard: (a) chain-level MAPE and WAPE trend (rolling 12 months); (b) store-level accuracy heatmap (green: MAPE < 15%, yellow: 15–25%, red: > 25%); (c) department-level accuracy ranking (which departments are hardest to forecast?); (d) bias detection: stores/departments with consistent over- or under-forecasting; (e) accuracy vs. target (target MAPE: < 15% at department level, < 10% at store level) | System | — | Automated |
| 3 | **Drift detection** (monthly): system runs automated drift detection tests: (a) **Data drift**: have the statistical properties of input features changed? (e.g., average transaction value shifted, promotional frequency changed, day-of-week purchasing pattern shifted); (b) **Concept drift**: has the relationship between features and sales changed? (e.g., payday weekend effect weakened as digital payments spread); (c) **Performance drift**: has forecast accuracy degraded beyond threshold? (MAPE increased > 5 percentage points from rolling 6-month average for 2+ consecutive months); if drift detected: system generates alert for Senior Data Scientist | System | — | Automated |
| 4 | **Monthly accuracy review**: Senior Data Scientist and Demand Planning Manager review: (a) which stores/departments have MAPE > 25% (red zone)?; (b) what are the root causes of large forecast errors? — new competitor opened near store? promotional event not captured in model? one-time event (local fiesta, typhoon closure)? supply-driven stockout (model forecasted demand but store was out of stock, so actual sales understated true demand)?; (c) identify stores/departments requiring manual forecast override for next month | Senior Data Scientist / Demand Planning Mgr | BI Manager | 2–4 hours/month |
| 5 | **Retraining trigger evaluation**: Senior Data Scientist evaluates whether drift detection alerts warrant model retraining: (a) **Retrain** if: performance drift confirmed at > 3 stores or > 2 departments chain-wide, or concept drift detected in key features, or seasonal pattern change detected (e.g., El Niño/La Niña shifting purchasing timing); (b) **No retrain** if: accuracy degradation is localized to 1–2 stores (local event), or within normal seasonal variation, or supply-driven (not forecast error); (c) if retrain: schedule retraining window (typically 1–2 weeks for data preparation, feature engineering, model training, validation, and deployment) | Senior Data Scientist | BI Manager | 1–2 hours/month |
| 6 | **Model retraining and deployment** (when triggered): (a) Senior Data Scientist prepares updated training dataset: include latest 12 months of data, remove obsolete features, engineer new features based on drift analysis; (b) train updated model on historical data; (c) validate on holdout period (last 3 months): compare new model accuracy vs. current model; (d) if new model outperforms: deploy to production; if not: investigate further and try alternative approaches; (e) A/B test: run old and new models in parallel for 1 month to validate improvement in live environment; (f) document model version, training data range, features used, and validation results in model registry | Senior Data Scientist | BI Manager | 20–40 hours/retraining |
| 7 | **Quarterly report to VP Supply Chain**: Senior Data Scientist presents quarterly forecasting accuracy summary: (a) chain-level MAPE trend, (b) inventory impact of forecast accuracy (estimated excess inventory cost from over-forecasting, estimated lost sales from under-forecasting), (c) model improvements made, (d) planned enhancements for next quarter | Senior Data Scientist | VP Supply Chain | 2 hours/quarter |

### System Touchpoints
- Forecasting accuracy engine: automated MAPE, WAPE, and bias computation per store-department (W1399.1)
- Accuracy dashboard: interactive heatmap with drill-down from chain → region → store → department (W1399.2)
- Drift detection module: statistical tests for data drift (Kolmogorov-Smirnov test), concept drift (Page-Hinkley test), and performance drift (threshold-based) (W1399.3)
- Model registry: version control for forecasting models with training data, features, hyperparameters, and validation results (W1399.6)
- Retraining pipeline: automated data preparation, training, validation, and deployment workflow (W1399.6)
- Integration with W1206 (AI demand forecasting model training), W1252 (supply chain predictive analytics), W2 (supply planning — forecast consumption), W4 (replenishment — forecast-driven), W1214 (store scorecard — accuracy KPI)

### Pain Points / Risks
- **Retraining frequency vs. model stability**: too-frequent retraining introduces instability (model parameters fluctuate based on recent noise); too-infrequent retraining allows drift to persist undetected; finding the right retraining cadence requires experimentation
- **Supply-driven vs. demand-driven accuracy**: if a store was out of stock on a popular SKU (supply failure, not forecast error), actual sales will be lower than true demand; the forecast accuracy metric penalizes the model unfairly; Demand Planning Manager must adjust accuracy metrics to exclude supply-constrained periods
- **New store ramp-up forecasting**: new stores (10–15 openings/year) have no historical data; the model must rely on comparable store data (similar market, similar size), which introduces higher uncertainty; accuracy targets should be relaxed for stores in their first 6 months
- **Promotional forecast complexity**: promotional events (W10, W12 double-points weekends) create demand spikes that are difficult to forecast if the promotional calendar changes year-over-year; model must incorporate promotional flags and historical promotional lift data

- System auto-generate of "generates alert for Senior Data Scientist" (replaces manual Step 3).
